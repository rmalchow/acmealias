## 5b. Sign-out lands on authentik, not the marketing site — DIAGNOSED, NOT FIXED

> Reproduced end to end and traced. Recording it precisely because the diagnosis was the expensive
> part and the symptom is easy to misattribute to our own logout route, which is correct.

- [x] 5b.1 **Fixed; the diagnosis below was right about the symptom and wrong about the cause.** The provider's `invalidation_flow` was `default-provider-invalidation-flow`, which ships with NO STAGES — it ends the application session, leaves authentik's own standing, and redirects. Correct for an SSO estate, wrong here. Now `default-invalidation-flow`, which carries a `UserLogoutStage`. Confirmed working. Original diagnosis: The chain is: our `GET /api/v1/auth/logout` 303s to the provider's `end-session` with `client_id` and `post_logout_redirect_uri` (correct); `end-session` 302s to the flow executor (correct); the executor completes with `{"component": "xak-flow-redirect", "to": "/"}` — **`/`, authentik's own root, NOT the `post_logout_redirect_uri` that was sent**. The person lands on authentik's page, which is what reads as "do you want to log back in"
- [x] 5b.2 **Answered: `id_token_hint` is mandatory, and `client_id` is not accepted in its place.** From 2026.8's own `end_session.py`: `# OIDC Certification: id_token_hint required with post_logout_redirect_uri`. Not a version quirk to work around — a certification requirement. The ID token is now stored on the session and sent once (`store.TakeLogoutHint`), and design D10's reasoning is amended rather than discarded: it is about ACCESS and REFRESH tokens, and an ID token is an audience-restricted assertion that buys nothing at the provider. Original: Find why the URI is dropped. `http://www.localhost` IS registered in the provider's `redirect_uris` with `matching_mode: strict`, and the request carries both it and `client_id` — the two things RP-initiated logout needs when there is no `id_token_hint`, which design D10 deliberately does not store. Candidates: authentik matching post-logout URIs against a separate list, a trailing-slash mismatch, or a version that requires `id_token_hint` regardless of the spec's `client_id` allowance
- [x] 5b.3 **Heeded, and it was the right warning.** The fix uses `default-invalidation-flow`, a flow authentik ships and maintains, precisely so no custom invalidation flow is introduced. Original: Do NOT solve it with a custom invalidation flow. That was tried: a flow with a `UserLogoutStage` and `authentication: none` makes the executor redirect TO ITSELF — an infinite loop, strictly worse than landing on the wrong page. The shipped `default-provider-invalidation-flow` completes correctly; only its destination is wrong
- [x] 5b.4 **Recorded, and it bit again** — this time as `!Find` for a recovery flow referenced by an identification stage defined above it, fixed by defining the flow first. Original: Note the ordering trap found alongside: blueprint entries apply IN ORDER, so a `!Find` for a flow defined below the provider that references it resolves to null and the entry fails with "This field may not be null" — naming the field, not the ordering
- [ ] 5b.5 **HALF OPEN.** `TestSignOutEndsBothSessions` covers the first half: the session dies at both ends and the browser is sent to the marketing site with a `post_logout_redirect_uri` authentik will honour. The second half — that signing in again sends a fresh authorization request to a FLOW rather than straight to the callback — is not asserted, and it is the half a redirect test misses: with the provider's session still alive, signing in again needs no password, and somebody on a shared machine has been told they are safe.
